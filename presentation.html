🚀 CI/CD — from commit to production

A guided tour of the pipeline in this repo: what runs, what it protects you from, and what actually breaks in the real world.

31 slides · interactive · press → to start

Frame the session: this session is about the decisions behind the pipeline rather than the tooling itself. Each stage answers one question: what can go wrong here, and which control catches it? The implementation lives in a separate repository (the lab); this deck covers the reasoning you would be expected to defend in a code review or an audit.

What SRE has been doing, step by step

This is not a new idea. It is a direction the industry has been walking for twenty years — and this pipeline is where that walk currently ends.

Manual release → Scripted release → Verify every change → Release automatically → Gated, evidenced delivery
Each step removed a specific failure mode: toil (people copying steps), drift (scripts that rot), integration risk (big infrequent batches), uncontrolled change (anything reaching production unverified), and finally unprovable change (no record of what shipped). The last one is why this is also an audit topic.
Do not lecture here — narrate. The question to put to the room: "which of these five steps does your organisation currently sit at?" Most organisations are between two and three, and the gap between "scripted" and "verified" is where audit findings live. The point to land: the pipeline is not a tooling preference, it is the answer to a series of specific failure modes, and it is also where the evidence trail comes from.

What is GitHub Actions?

It is a CI/CD platform that runs on GitHub.

You describe the pipeline as a YAML file inside the repository. GitHub reads that file, starts a machine per job, and executes the steps. Nothing to install, nothing to maintain, no server of your own.

Free for public repositories. The YAML file is the entire interface.

It is not:

• a testing tool (it can run them)
• a deployment tool (it can publish)
• where your code lives (that is the repository)
• software you install on a server (unless you choose self-hosted runners)

It is one of several, and the choice is mostly about where your code already lives — not about capability.
Answer the Jenkins question directly, because it is the one people actually ask. Jenkins is the long-standing default: self-hosted, plugin-based, configured through its own interface, and still very common in larger enterprises. GitHub Actions is usually chosen because the code is already on GitHub and the configuration travels with it. GitLab CI is the equivalent for GitLab; CircleCI, Azure Pipelines, Travis and Buildkite fill the same space. The concepts transfer directly — learn the model here and you can read any of them.

Is it CI or CD? Where is the line?

CI — Continuous IntegrationCD — Continuous Delivery / Deployment

In our lablint + testbuild → deploy → smoke

Both halves live in one workflow file. Which half you are in is decided by the trigger and the gate — not by the product you chose.
The confusion is understandable: the product is called "Actions" and covers both halves. The precise wording also matters for an audit conversation: continuous deployment releases without human involvement, continuous delivery means the change is continuously ready and a person approves the release. Ours is continuous deployment until a required reviewer is added to the production environment — and that single setting change is the whole difference.

Job 1 · Lint — the rules the team agreed on

A linter is a program that reads your code and applies a list of rules your team has written down. It never runs your code. It answers one question: does this file follow the rules we agreed?

SYNTAX every file parses — a missing brace would break the build

WIRING the page still has the element IDs the script looks for

CONSISTENCY the command the pipeline calls still exists

SECRETS no credential-shaped text has been committed

WORKFLOW SHAPE the pipeline YAML uses keys the platform accepts

50 checks in total. A linter is not a style opinion — it is a list of rules, a message, and an exit code.

Keep this plain. A linter is not "the robot judge" — it is a rulebook turned into a program. Each of the five groups corresponds to a rule someone actually wrote down, and each one exists because it caught a real mistake. If the audience asks "why not just use ESLint?" — you can, and for many projects you should; the point of the lab is that the shape of a linter is the same whether the rules come from ESLint or from your own team.

What a failure actually looks like

A renamed element ID — a two-character change — and the check refuses to let it through.

$ npm run lint
✔ syntax OK: counter.js
✔ syntax OK: app.js
✔ index.html links style.css
✔ index.html loads app.js as an ES module
✖ index.html has id="count"
✔ index.html has id="magic-button"
✔ index.html has id="reset-button"

Lint FAILED with 1 problem(s). Fix, commit, push.
The exit code is the contract: 0 = pass, non-zero = fail. That single number is what turns the job red and blocks everything downstream — and what makes the check usable by a machine rather than by a person reading a log.
This is real output from the linter in this repository, produced by deliberately renaming an element ID. Two points to make: the message names the exact rule and the exact element, so the failure is actionable without reading further; and the non-zero exit code is what makes the failure machine-readable. A check that only prints text without returning a status is documentation, not a control.

Job 2 · Test — and the same job run twice

One node in the graph, two jobs in the list. The interface groups them.

A test is one stated expectation — "the counter starts at 0", "a non-integer start is rejected" — written so that it can only pass or fail.

A matrix runs one job several ways. Here the same test suite runs on Node 20 and Node 22, so the claim "supports Node 20+" is verified rather than asserted.

8 unit tests on the counter · 4 integration tests on the linter itself

Two ideas here. First, a test is a stated expectation, not a script — "the counter starts at 0" is an assertion that either holds or does not. Second, the matrix: one job definition, several configurations, and the interface collapses them into a single node labelled "Matrix: test · 2 jobs completed". If a change breaks only Node 22, both legs stay visible in the run list, so nobody has to guess which runtime failed. Also note the fourth test type: testing your own tooling, because a check that cannot fail is not a control.

Job 3 · Build — the artifact

  • dist/ is the artifact — the only thing the deploy job is allowed to publish. It never reads your source.
  • Immutable — once built, the artifact cannot change. What is deployed is exactly what was verified.
  • Labelled — BUILD_INFO.json carries the version, the build time and the commit ID.
  • Reproducible — the same input produces the same output. If it is not reproducible, "it passed in CI" means nothing.
The commit ID inside the artifact is how you answer "which code is live?" without guessing. That is what the smoke job checks afterwards.
The habit to introduce: build once, publish the same bytes everywhere. If the staging release and the production release are built separately, then what was tested is not what shipped, and the audit trail becomes a reconstruction rather than a record. Also mention that the commit ID written into the artifact is a small thing with a large payoff: it turns "which version is live?" from a question into a lookup, and it is the basis of the smoke check on the next slide.

Job 4 · Deploy — identity, not passwords

OIDC instead of a stored secret

The runner mints a short-lived token proving "I am this repository's workflow". Nothing is stored, nothing leaks, nothing has to be rotated.

id-token: write pages: write

environment: production

Names the target. In Settings → Environments you can attach protection rules: required reviewers, a wait timer, branch restrictions.

Add a reviewer → continuous delivery.

Least privilege is a budget: the deploy job can write, every other job is read-only. A compromised check cannot publish.
OIDC is the most significant change in modern pipeline security: before, every pipeline needed a long-lived token stored in repository settings, copied between organisations, rotated by hand, and occasionally leaked in a screenshot. Now the platform vouches for the workflow itself and issues a token that expires in minutes. The environment is the second half of the story: it is where "who is allowed to release production" is configured, and it is a control an auditor can see.

The gate — one line, three behaviours

Click a tab. This is the same if: line producing all three outcomes.

lint ✅ · test ✅ · build ✅ · deploy ⏭️ · smoke ⏭️

A PR is a proposal. The automated checks run; nothing is published. Merging to main is what triggers the release.

lint ✅ · test ✅ · build ✅ · deploy ✅ · smoke ✅

A push to main is a release: the whole chain runs, and the smoke job proves the live site responds.

same as push to main if you start it on main

The gate checks branch and event type — not "was it a push". On any other branch it stops after build. Worth knowing before you demo it.

This is the single most important slide for a reviewer: one line of YAML encodes a policy about who may publish. The question to put to the room: what would you add if a developer without release authority could push to main? Answer: branch protection, required reviews and environment reviewers — all three are settings, not code, and all three are visible to an auditor.

The gate, as recorded

A run from a branch other than main: the release step is skipped, and the run still counts as successful.

Both screenshots are from this repository's own run history. Point out the distinction between skipped and failed, because the two are easy to conflate in a report: failed means the step ran and did not succeed; skipped means the condition excluded it. Also note that the overall run is still marked successful — the pipeline did exactly what it was asked to do. For an auditor this is a clean demonstration that the control is enforced by the platform and not by people remembering to behave.

Job 5 · Smoke — success is not the same as working

A successful pipeline means the steps exited 0. It does not mean a user can load the page.

curl -fsSL --retry 10 --retry-all-errors --retry-delay 5 "$URL"   # 1. reachable (Pages propagates late)
grep -q "magic-button" /tmp/index.html                                  # 2. it is OUR page
test "$DEPLOYED" = "$GITHUB_SHA"                                         # 3. built from THIS commit
The smoke job is the only one that looks at the result rather than the process. It can turn the run red after a successful release — which is exactly when you want to know, because the remedy is still minutes away.
This job exists because of the gap between "the deploy command succeeded" and "the site works for users". The three assertions are deliberately simple: reachable, correct content, built from this commit. Mention the retry: hosting platforms take seconds to propagate, so the checker needs patience as well as the deploy does. And mention that this is the cheapest incident detection available: minutes instead of a user report.

How this fits into a team's day

Author — branch, push, open PR, fix a failed check.

Reviewer — reads the difference. A human gate; CI is a machine gate. Neither replaces the other.

Release owner / on-call — owns what happens when a release breaks.

Platform team — owns the pipeline itself. If every repository has the same 200 lines, they extract it into a reusable action or a template repository.

branch → push → PR → review → required status checks green → merge to main → release → verify

A pipeline is not only YAML — it is a team agreement encoded in YAML. New developers are usually caught out by the "who merges what" question rather than the syntax. Name the roles out loud and name who owns the pipeline file; in a small team that is you, and knowing that is part of the job.

Protect main — where the gate becomes real

  • Settings → Branches → Add rule → branch name main
  • ☑ Require status checks to pass — tick lint, test, build
  • ☑ Require pull requests — no direct pushes
  • ☑ Require branches to be up to date — no stale merges
The gate in code can be bypassed by anyone with write access. Repository settings cannot be bypassed by accident — which is why the control needs both halves.
Ask the room to try it on the fork afterwards: open a PR with a failing test and attempt to merge — the platform refuses, with a link to the failing check. That refusal is the same mechanism that blocks an emergency change at 2am, which is also why teams agree an emergency path in advance: break glass, revert, fix forward, and record it.

What actually breaks in real pipelines

FailureWhat it looks likeWhat we do about it
Flaky testfails intermittentlyfix or remove it — never retry blindly

Secret expirythe release fails at authenticationprefer OIDC; rotate whatever remains

Cache poisoningunexpected build output from a branchscope caches; never cache credentials

This is the slide that separates "I followed a tutorial" from "I have seen an incident". Each row is a real class of failure. The principle to teach: prefer controls that fail loudly and early — lint, tests, smoke — over discovering the problem from a user report. And on flakiness specifically: a test that fails intermittently trains the team to accept red results, which destroys the value of every other check in the pipeline.

Security practices that actually matter

  • Least privilege per job — only deploy can write; everything else is read-only.
  • No long-lived secrets — OIDC for Pages; real secrets in Settings → Secrets, never in the repository.
  • Treat pull requests from forks as untrusted input — a fork's code runs on the runner. Never run untrusted code with a write-scoped token (pull_request_target is the classic trap).
  • Pin your actions — @v4 is readable; a full commit ID is safe. Know the trade-off.
  • Assume every commit is permanent — deleting a file does not delete it from history; rotate anything that was exposed.
The pull_request_target trap is worth a moment of attention: that trigger runs your workflow with your token and secrets against code from the pull request, which is how production keys have been exposed in the wild. The rule of thumb is short: untrusted code plus a write-scoped token is never acceptable. The lint rule that fails a build when a credential-shaped string is committed is the small, automatable version of the same habit.

Cost, quotas and caching

Public repositories → free hosted runners.

Private repositories → a monthly minutes allowance (~2,000 on GitHub's Free plan — check current pricing; the number changes).

Minutes are wall-clock time. A job that hangs for 10 minutes costs 10 minutes.

→ that is why every job here sets timeout-minutes: 10.

Caching reuses downloaded dependencies between runs.

This lab has zero dependencies — so there is nothing to cache, and every runner starts immediately.

Caches are shared across branches: a poisoned cache is a real supply-chain risk.

Self-hosted runners: no minute limits, but now you own patching, isolation and cleanup.

Cost conversations come up in every governance review. Three levers: fewer minutes (cache, keep the matrix small, keep jobs fast), cheaper minutes (larger runners cost more per minute but can finish sooner), or your own hardware (self-hosted). Our matrix doubles the test job's minutes — worth it here, not always worth it for a ninety-minute suite. Note that the zero-dependency design is a deliberate teaching choice, not an accident: it is why the lab installs instantly on any machine.

CI/CD is not "we have a pipeline". It is smaller batches, more often, safer each time. A pipeline that takes 40 minutes trains people to batch large changes — the opposite of the intended outcome.
If asked how you know the CI/CD approach is working, the answer is these four numbers and their trend. The counter-intuitive lesson: making the pipeline faster reduces lead time, but the bigger win is making it reliable, because a pipeline people distrust gets ignored. Also worth saying plainly: these metrics are measures of the delivery system, not of individuals — they are diagnostic, never a performance target for a person.

Recap 🎓

  • 📝 Code → 🔍 CI (lint + test, on every runtime) → 📦 artifact → 🚚 CD (release) → 🌐 verify
  • 🔒 Least privilege + OIDC instead of stored secrets
  • 🚦 The gate = branch + event type (+ repository protection rules)
  • 🧪 Smoke test = a successful run is not a working site
  • ⏪ Rollback = git revert + push. Normal operation, not a crisis.
Homework: break the lab on purpose. Break a test, break the HTML wiring, commit a credential-shaped string — and observe which job catches it. A failure you can explain is a control working as designed; one you cannot explain is a finding waiting to be raised.
Close by naming the next steps for a real service: a staging environment, dependency caching, an end-to-end test with a real browser, and a release workflow that tags a version. Each is a small addition to what exists here — which is the whole point: continuous delivery is not a product you buy, it is a set of controls you add one at a time, each of which you can evidence.

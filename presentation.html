🚀 CI/CD — from commit to production

A guided tour of the pipeline in this repo: what runs, what it protects you from, and what actually breaks in the real world.

23 slides · interactive · press → to start

Frame the session: this is not a tool tour, it is a decision tour. Every stage answers one question — "what could go wrong here, and who catches it?" The yellow robot work happens in a separate repo (the lab); this deck explains the reasoning you would be asked to defend in a code review.

Why pipelines exist

  • Integration hell — 40 people merge into one branch; main breaks daily, and everyone blames "someone else's" commit.
  • Manual release — the same 12 steps every Friday; forget one file and Friday is broken.
  • Slow feedback — the bug is found by a user, three days after the commit.
Every stage of a pipeline exists to attack one of these three. When a stage has no failure mode it protects against, it is ceremony — delete it.
Ask the room: how many manual steps does your release have? That number is your risk surface. CI/CD is not about speed for its own sake — it is about shrinking the number of things a human can forget.

The vocabulary you will be asked about

TermWhat it actually means
CI — Continuous IntegrationEvery change is verified automatically (lint + test) before it is allowed to merge.
Continuous DeploymentGreen on main → it ships, unattended.
Continuous DeliveryGreen on main → it is ready to ship; a human approves the release.
PipelineThe whole chain of jobs: commit → lint → test → build → deploy → smoke.
GateA condition that decides whether a job runs. Ours: if: on main and not a PR.
ArtifactThe built, immutable output (dist/) handed from build to deploy.
The distinction people get wrong in interviews: delivery vs deployment. Both are "CD". The difference is only whether a human presses the button — and that is a risk decision, not a technical one. Ours is continuous deployment until you add a required reviewer to the production environment.

How GitHub Actions actually works

1. Event — a push, a PR, a schedule.

2. Workflow — the YAML file in .github/workflows/ that says what to do.

3. Runner — a fresh, throwaway VM. One per job. Destroyed afterwards — state never leaks between runs.

4. Job → steps — each step is one command or one action.

# the smallest possible workflow
on: [push]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - run: npm run build

A workflow is just YAML the platform interprets. The runner is not your laptop — it is a clean machine, every time.

The "ephemeral runner" idea is the one that changes how you debug: you cannot SSH into a runner, and you cannot rely on a file you left there yesterday. Everything the job needs must be in the workflow or fetched by it. That is why the pipeline re-installs Node every single run.

The pipeline, end to end

📦 Commit → 🔍 Lint → 🍪 Test → 📦 Build → 🚚 Deploy → 🌐 Smoke

lint ∥ test (parallel) → build → deploy → smoke

Parallel jobs save wall-clock time. The chain after them is a dependency graph: each job declares what it needs, and GitHub works out the order.
Point at the graph, not the boxes: lint and test have no `needs:` so they start together; build has `needs: [lint, test]` so it waits for both. When one fails, the rest are skipped — grey, not red. Skipped is a different signal from failed: skipped means "we never got there", failed means "we tried and it broke".

Job 1 · Lint — rules, not opinions

A linter is a program that reads your code and complains about things your team decided to complain about.

SYNTAX every shipped file parses (a missing brace is a build-stopper)

WIRING index.html still has the ids app.js expects

CONSISTENCY every npm run X in the workflow still exists in package.json

SECRETS no credential-shaped string is committed

50 checks, zero dependencies. ESLint is the same idea with 300 rules — the shape is identical: a rule, a failure message, an exit code.
"Consistency" is the check people underestimate: rename an npm script locally, forget the workflow, and CI dies with a confusing "command not found" instead of a clear message. The secret scan is the other one worth automating — humans are bad at not committing .env files, machines are great at it.

Job 2 · Test — and the matrix

LayerWhat it meansHere
Unitone function, no I/O, milliseconds8 tests on createCounter
Integrationyour code + another real piece (here: the linter as a subprocess)4 tests on lint.js
E2Ea real browser clicking the real page❌ not here

MATRIX the test job runs twice — Node 20 and Node 22 — so one green check becomes two. fail-fast: false keeps both running so you see every broken runtime at once.

A matrix is the cheapest insurance in CI: your code must pass on every runtime you claim to support. When the matrix fails, read WHICH leg failed — a matrix failure is often version-specific, not logic-specific. Also flag: a test that cannot fail is worse than no test, and a flaky test is a bug, not bad luck — a flaky red trains people to ignore red.

Job 3 · Build — the artifact

  • dist/ is the artifact — the only thing the deploy job is allowed to publish. It never reads your source.
  • Immutable — once built, the box cannot change under you. What you deploy is exactly what you tested.
  • Labelled — BUILD_INFO.json carries version, build time and the commit sha.
  • Reproducible — same input, same output. If it is not reproducible, "it worked in CI" means nothing.
The commit sha inside the artifact is how you answer "which code is live?" without guessing. That is what the smoke job checks later.
Artifacts are why "build once, deploy many" exists: the staging deploy and the production deploy must run the SAME bytes, otherwise what you tested is not what shipped. Also mention: in a real project you version artifacts (semver + sha) and keep old ones, because rollback needs the previous artifact, not a rebuild.

Job 4 · Deploy — identity, not passwords

OIDC instead of a stored secret

The runner mints a short-lived token proving "I am this repo's workflow". Nothing is stored, nothing leaks, nothing to rotate.

id-token: write pages: write

environment: production

Names the target. In Settings → Environments you can attach protection rules: required reviewers, wait timer, branch limits.

Add a reviewer → continuous delivery.

Least privilege is a budget: the deploy job gets write access, every other job gets read-only. A compromised lint step cannot publish.
OIDC is the single biggest change in modern CI security: before, every pipeline needed a long-lived PAT sitting in repo settings, copied between orgs, rotated by hand, and occasionally leaked in a screenshot. Now the platform vouches for the workflow itself. If you ever add a real secret, it goes in Settings → Secrets, never in the repo — and our linter fails the build if a credential-shaped string shows up in a commit.

The gate — one line, three behaviours

Click a tab. This is the same if: line producing all three outcomes.

lint ✅ · test ✅ · build ✅ · deploy ⏭️ · smoke ⏭️

A PR is a proposal. The robots check it; nobody publishes it. Merging to main is what triggers the release.

lint ✅ · test ✅ · build ✅ · deploy ✅ · smoke ✅

A push to main is a release: the whole chain runs, and the smoke job proves the live site answers.

same as push to main if you start it on main

The gate checks branch and event type — not "was it a push". On any other branch it stops after build. Honest behaviour, and worth knowing before you demo it.

This is the single most important slide for a reviewer: the gate is one line of YAML — `if: github.ref == 'refs/heads/main' && github.event_name != 'pull_request'` — but it encodes a policy about who may publish. Ask: what would you add if a junior could push to main? (Answer: branch protection + required reviews + environment reviewers.)

Job 5 · Smoke — green is not the same as working

A green pipeline means the steps exited 0. It does not mean a user can load the page.

curl -fsSL --retry 10 --retry-all-errors --retry-delay 5 "$URL"   # 1. reachable (Pages propagates late)
grep -q "magic-button" /tmp/index.html                                  # 2. it is OUR page
test "$DEPLOYED" = "$GITHUB_SHA"                                         # 3. built from THIS commit
The smoke job is the only one that looks at the result instead of the process. It can turn the pipeline red after a successful deploy — which is exactly when you want to know, because the fix is still minutes away.
This job exists because of the gap between "the deploy command succeeded" and "the site works". Real systems extend it: synthetic monitoring, error-rate alerts, and automatic rollback when the smoke test fails. Mention the retry: GitHub Pages takes seconds to propagate, so the checker needs retry logic too — eventually-consistent systems need the CHECKER to be patient, not just the deploy.

How this fits into a team's day

Author — branch, push, open PR, fix red CI.

Reviewer — reads the diff. A human gate; CI is a machine gate. Neither replaces the other.

Release owner / on-call — owns what happens when a deploy breaks.

Platform team — owns the pipeline YAML. If every repo has the same 200 lines, they extract a reusable action or a template repo.

branch → push → PR → review → required status checks green → merge to main → release

The pipeline is not just YAML, it is a team agreement encoded in YAML. New developers usually get burned by the "who merges what" question, not by the YAML. Say the roles out loud and name who owns the pipeline file — in a small team that is you, and knowing that is part of the job.

Protect main — where the gate becomes real

  • Settings → Branches → Add rule → branch name main
  • ☑ Require status checks to pass — tick lint, test, build
  • ☑ Require pull requests — no direct pushes
  • ☑ Require branches to be up to date — no stale merges
YAML can be bypassed by anyone with write access. Repo settings cannot be bypassed by accident — which is why the gate needs both halves.
Do this on your fork as exercise: try to merge a red PR and GitHub refuses with a link to the failing check. That refusal is the same mechanism that stops a hotfix at 2am from shipping untested code — and it is also the mechanism that can block you, so teams agree an emergency path (break glass, revert, fix forward) in advance.

What actually breaks in real pipelines

FailureWhat it looks likeWhat we do about it
Flaky testred 1 run in 20fix or delete it — never retry blindly
Propagation delaydeploy green, site still oldretry in the checker (our smoke job)
Secret expirydeploy fails at authprefer OIDC; rotate what remains
Runner OOMjob killed, no log tailbigger runners, smaller matrix
Cache poisoningweird artifacts from a branchscope caches; never cache secrets
Force-push to mainlost history, broken PRsprotect branches; use git revert
This is the slide that separates "I followed a tutorial" from "I have seen an incident". Every one of these is a real class of failure. The pattern to teach: prefer tools that fail loudly and early (lint, tests, smoke) over tools that fail silently and late (a user reports the bug).

Security practices that actually matter

  • Least privilege per job — only deploy can write; everything else is read-only.
  • No long-lived secrets — OIDC for Pages; real secrets in Settings → Secrets, never in the repo.
  • Treat fork PRs as hostile — a PR from a fork runs their code. Never run untrusted code with a write-scoped token (pull_request_target is the classic trap).
  • Pin your actions — @v4 is readable; a full commit SHA is safe. Know the trade-off.
  • Assume every commit is public — deleting a file does not delete it from history; rotate it.
The pull_request_target trap is worth 60 seconds: that trigger runs your workflow with your token and secrets against the PR's code — which is how people accidentally expose production keys. The rule of thumb: untrusted code + write-scoped token = never. Our linter's secret scan is the small, automatable version of the habit.

Cost, quotas and caching

Public repos → free hosted runners.

Private repos → a monthly minutes allowance (~2,000 on GitHub's Free plan — check current pricing; the number changes).

Minutes = wall-clock time. A job that hangs for 10 minutes costs 10 minutes.

→ that is why every job sets timeout-minutes: 10.

Caching reuses downloaded dependencies between runs.

This lab has zero dependencies — so there is nothing to cache, and every runner starts instantly.

Caches are shared across branches: a poisoned cache is a real supply-chain risk.

Self-hosted runners: no minute limits, but now you own patching, isolation and cleanup.

Cost conversations come up in every org review. The three levers: fewer minutes (cache, smaller matrix, faster jobs), cheaper minutes (bigger runners are 2-8x the price but can be faster per job), or your own hardware (self-hosted). Our matrix doubles the test job's minutes — worth it here, not always worth it for a 90-minute suite.

Change failure ratewhat % of deploys cause an incident?every release needs a hotfix
Time to restorewhen it breaks, how fast is it fixed?rollback takes hours
CI/CD is not "we have a pipeline". It is smaller batches, more often, safer each time. A pipeline that takes 40 minutes trains people to batch huge changes — the opposite of the goal.
If you are asked "how do you know your CI/CD is working?" — these four numbers, and their trend. The counter-intuitive lesson: making the pipeline faster reduces lead time, but the bigger win is making it reliable, because a pipeline people distrust gets ignored. Teams game all four metrics; the honest answer is to look at them together.

Recap 🎓

  • 📝 Code → 🔍 CI (lint + test, on every runtime) → 📦 artifact → 🚚 CD (deploy) → 🌐 verify
  • 🔒 Least privilege + OIDC instead of stored secrets
  • 🚦 The gate = branch + event type (+ repo protection rules)
  • 🧪 Smoke test = green steps are not a working site
  • ⏪ Rollback = git revert + push. Normal operation, not a crisis.
Homework: break the lab on purpose. Break a test, break the HTML wiring, commit a fake secret — and watch which job catches it. A red X you caused is a lesson; a red X you cannot explain is a pager.
Close by naming the next steps for a real project: a staging environment, dependency caching, an E2E test with Playwright, and a release workflow that tags a version. Each of those is one small addition to what exists here — which is the whole point: CI/CD is not a product you buy, it is a habit you build one gate at a time.
